# presets

검토 기준 데이터. 엔진 코드에 팀명·양식번호·필드명 하드코딩 금지, 항상 주입한다.

## 검토 기준 — 3층

한 번 검토할 때 **공통 + 그 팀 + (있으면) 업로드**를 합쳐 쓴다
(`preset/library.py:compose_review_preset`).

| 층 | 자리 | 누가 고치나 |
|---|---|---|
| 공통 | `criteria/common.yaml` | 고정. 모든 팀·문서에 항상 적용 |
| 팀별 | `criteria/teams/<팀>.yaml` | 팀마다 하나. 수정·추가 가능 |
| 업로드 | `.docreview/criteria/uploads/<id>.json` | 검토할 때 사용자가 올린다 |

**층은 파일 위치가 정한다.** 파일 안의 `scope` 값은 읽지 않는다 — `teams/` 에 둔
파일이 `scope: 공통` 이라고 적혀 있으면 그건 실수이고, 그 실수가 조용히 통하면
공통 기준이 한 팀에서만 도는 것을 아무도 눈치채지 못한다.

업로드는 예외가 아니라 **출발점**이다. 기준이 아직 정리되지 않은 팀이나
프로젝트마다 기준을 조정하는 팀(AX품질팀 업무 프로세스가 그렇게 쓴다)은 업로드로
시작하고, 반복되는 것이 팀 기준으로 굳는다.

### 파일 모양

```yaml
name: AI시험인증1팀
team: AI시험인증1팀              # 팀별일 때만
source_filename: ...            # 어디서 왔나 (되짚기용)

outputs:                        # (선택) 대상별 문서 지도 — 값을 어디서 뽑나
  - key: 갑지
    form_no: "SST-K-TP-7-08-06(00)"
    fields: [{name: 기관명, from: table, labels: [기관명], at: right}]

items:                          # 검토 기준 항목 — 무엇을 검사하나
  - 'no': "12"
    text: |-
      여러 줄 설명은 블록으로 쓴다
    group: 문서 양식 검토
    agent: 형식·완전성          # 관점 라벨. mode 기본값을 정한다
    mode: 규칙                  # 규칙 | LLM-조각 | LLM-문서 | 사람
    check: field_presence       # 규칙일 때 **무엇이** 검사하나
    params:                     # 그 검사에 줄 값 (코드에 안 박는다)
      fields: [작성자, 검토자]
    source: 문서검증 No.12
```

### mode 와 check

`agent` 는 관점이지 라우팅이 아니다. **규칙 기준은 `check` 로 자기를 검사할 규칙의
이름을 댄다** — 안 대면 검사기가 안 붙고 화면에 "이 기준을 검사하는 규칙이 아직
없습니다"로 뜬다. 쓸 수 있는 이름은 `src/modules/agent_checklist/README.md` 에 있다.

라벨로 잇던 예전 방식은 "형식·완전성" 하나에 EV2 의 규칙 기준 15개를 매달았고,
검사기 둘의 지적이 15개 전부에 복사됐다. 하나짜리 결함이 열다섯 건으로 보였다.

**규칙을 모르면 비워 둔다.** 예: EV2 19번(파일명)은 본문이 "내부 규칙에 맞게"까지만
말하고 그 규칙이 어디에도 없다. 형식을 지어내 넣으면 멀쩡한 파일명이 전부 틀린
것으로 뜬다 — 아래 `checklists/` 가 그렇게 만들어졌다가 지워졌다.

`items` 만 있으면 되고 `outputs` 는 산출물·계통·단계처럼 **대상 단위**가 있는 팀만
쓴다. 대상 단위는 팀마다 다르다 — AI시험인증1팀은 산출물 10종, 에너지검증팀은
문서유형 12종 + 계통, AX품질팀은 생명주기 단계 3종.

### 기준은 이 파일들이 진실이다

처음 한 번은 팀 요구사항 엑셀에서 옮겨 왔지만, **지금은 이 yaml 이 원본이다.**
기준을 고칠 곳은 엑셀이 아니라 여기다(2026-07-30 확정).

옮겨 오는 스크립트는 지웠다(2026-08-06). 엑셀에는 `mode`·`check`·`note` 열이 없어
사람이 판단해 채워야 했는데, 스크립트를 다시 돌리면 `items` 절을 통째로 갈아끼워
그 판단이 날아갔다. 엑셀을 더 갱신하지 않기로 해서 도구째 없앴다.

**이 디렉터리는 git 으로 추적한다.** 원본 xlsx 는 `data/*` 로 무시되므로 여기 담긴
yaml 이 유일한 사본이다. 담긴 것은 검토 규칙과 문서번호이지 고객 문서 내용이
아니다 — 문서 원본은 `data/*` 로 계속 막는다.

## checklists/ — 지웠다

`checklists/*.yaml` 은 이름이 체크리스트지만 **내용은 검사 설정**이었다(요건 ID 정규식,
담당 범위, 일관성 agent 그룹). `settings.toml` 의 `[review] checklist` 가 하나를 고정으로
가리켰다.

특정 문서를 보고 거꾸로 뽑은 값이라 **순환**이었다 — 문서에서 뽑은 잣대로 그 문서를
재면 틀릴 수가 없다. 실제로 `acmd.yaml` 의 `id_pattern` 은 ACMD 상세설계서가 선언한
규칙("분류구분")이 아니라 실제 쓰인 형식("세부기술번호")을 옮긴 것이어서, 그
불일치(LLM 이 잡아낸 실제 결함)를 정답으로 굳혀 놓았다.

지금은 매개변수를 기준이 `params` 로 정한다. 옮겨간 자리:

| 옛 값 | 지금 |
|---|---|
| `required_sections` | EV2 40번의 `params.required_sections` (본문이 근거를 적고 있다) |
| `id_pattern` | **아무 데도 없다** — 어느 팀 기준도 ID 형식을 적지 않는다 |
| `placeholder_markers` | ax-quality 9번의 `params` (그 팀만 요구했다) |

`id_pattern` 이 비어 있으면 문서 비교는 돌지 않고 **"요건 ID 형식이 검토 기준에 없어
추적성 검사를 수행하지 않았습니다"** 로 뜬다. 팀이 형식을 알려주면 그 기준의
`params.id_pattern` 에 적는다. `scope_pattern`(이 부분 설계서가 담당하는 요건 범위)은
문서쌍마다 달라 팀 기준에 못 넣고 **검토 요청 시 입력**이어야 한다.
